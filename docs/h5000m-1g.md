# Hiveton H5000M 1G/8GB 稳定精简基线

本板型从 `h5000m-stable-2026.07.17` 的已验证 H5000M 基线派生，仅覆盖 1 GiB
DDR 和 `8GTF4R` eMMC 所需的硬件差异。板型 ID 为
`hiveton,h5000m-1g`，不与 4G/256GB 型号共用镜像。
本仓库只导出 1G/8GB 的设备、BL2 和 U-Boot 构建目标，不生成也不校验 4G
版本产物；两个硬件版本分别由各自项目维护。

## 内存与启动地址

- DRAM：`0x40000000` 起始，长度 `0x40000000`（1 GiB）。
- Linux kernel load：`0x40000000`。
- U-Boot/FIT load：`0x48000000`。
- DTB load：`0x4ff00000`。
- `CONFIG_SYS_BOOTM_LEN=0x6000000`，production 和 recovery FIT 均不得超过
  96 MiB。
- BL2 使用 MediaTek `emmc-comb` DDR 初始化；eMMC 在 BL2、U-Boot 和 Linux
  中继续采用已验证的 DDR52 策略，不启用 HS200/HS400。
- 首次检测到无效冗余 U-Boot 环境时，系统从板级环境清单一次性初始化两个
  env 副本，避免 `fw_envtools` 的通用 distro-boot 回退值进入持久环境。

## 固定 GPT

该布局只接受总容量为 `15,269,888` 个 512 字节扇区的 `8GTF4R`。GPT 主表
位于设备开头，备份表必须写到设备末尾。

| 分区 | 起始扇区 | 结束扇区 | 大小 | 类型 |
|---|---:|---:|---:|---|
| ubootenv | 8192 | 9215 | 512 KiB | Linux filesystem |
| factory | 9216 | 17407 | 4 MiB | Linux filesystem |
| fip | 17408 | 25599 | 4 MiB | EFI System |
| recovery | 32768 | 294911 | 128 MiB | Linux FIT |
| production | 294912 | 15269854 | 14,974,943 扇区（约 7.1406 GiB） | Linux FIT |

不创建 `data` 或旧版 `p128` 分区。rootfs 构建上限为 7311 MiB，剩余不足
1 MiB 的空间保留给扇区取整和 GPT 边界。production 内由 fitblk 提供 F2FS
overlay；系统不安装 `block-mount`、`e2fsprogs`，也不生成 userdata 自动挂载
配置。

## 软件边界

保留 MTK HNAT、WARP/WED、MT7992/MT799A、BBR、完整 USB 蜂窝栈、CPU-only
fancontrol、MTK-only TurboACC、`dnsmasq-full`、`wpad-openssl`、LuCI 软件管理和
`uboot-envtools`。保留 `kmod-br-netfilter` 及其最小内核依赖，用于安装 OpenWrt
标准的 `/etc/sysctl.d/11-br-netfilter.conf`；桥接流量的 arptables、IPv4 和 IPv6
netfilter hook 默认均为 0，避免 MTK HNAT 与透明代理同时运行时无线桥流量进入
重复处理路径。这不表示默认启用桥防火墙。默认 TCP CCA 仍为 cubic，BBR 可由
用户选择。

为保证系统升级后仍能正规使用当前的 Nikki 透明代理配置，基线保留其所需的
`dummy`、`inet-diag`、socket/tproxy、nft socket/tproxy 和 TUN 通用内核模块。
它们与固件内核 ABI 同步；Nikki、Mihomo、Subpipe、ByeDPI 和 FRPC 等用户态
程序仍不是基线组成，仅在设备运行态按需安装。

不包含 Nikki、subpipe、zapret2、通用 Full-cone、VPN/容器/IPVS/UDP tunnel、
MTD/UBI 工具、userdata/ext4 管理工具。firewall 的 IPv4/IPv6 Full-cone 默认值
均为 0，内核不包含 BCM/XT/nft Full-cone 实现。

## 构建与校验

```sh
./scripts/feeds update -a
./scripts/feeds install -a
cp config/h5000m-1g-minimal.config .config
make defconfig
./scripts/h5000m-1g-verify
make -j$(nproc)
./scripts/h5000m-1g-verify --artifacts
```

产物前缀为 `immortalwrt-mediatek-filogic-hiveton-h5000m-1g`，包括 production
sysupgrade、initramfs recovery、主/备 GPT、BL2 和 FIP。2026-07-18 的完整
哈希、尺寸及旧版差异见 `docs/h5000m-1g-artifact-review.md`。

## 首次迁移限制

旧 1G GPT 的 recovery/production 区域与本布局重叠，因此首次迁移不能
直接在旧系统执行普通 sysupgrade。2026-07-18 已在只有 SSH 的条件下，
利用旧 U-Boot 的 recovery 回退能力完成了一次受控的两阶段迁移：

1. 在旧分区表下写入新 recovery，临时将启动顺序设为 recovery 优先，
   并进入纯内存 initramfs。
2. 在 initramfs 中依次写入 production、recovery、FIP、BL2，最后写入
   备份和主 GPT；全程保留 factory，并对关键区域做定长回读校验。
3. 清理旧环境后从 FIP 内置板级默认值启动，再初始化冗余持久环境。

该流程依赖旧启动链的 recovery 回退能力和可用 SSH，不是对任意未知旧版
设备的通用无串口方案。对其他尚未迁移的设备，仍应优先使用串口监控，先备份
factory/启动链/分区表，再进行完整迁移。完成新布局安装后，后续日常
升级只写 production。实机结果见 `docs/h5000m-1g-flash-validation-2026-07-18.md`。

H5000M 的 fitblk/F2FS 布局要求配置归档写在页面对齐后的 SquashFS 末尾，即
`/dev/fitrw` 的起始扇区，而不是完整 FIT 的填充末尾。升级脚本会从新镜像的
SquashFS superblock 计算该位置，再由 preinit 恢复 `sysupgrade.tgz`；这保证
日常 sysupgrade 在 rootfs 尺寸变化时也能保留 UCI、无线和应用数据。
