# Hiveton H5000M 构建与存储布局

本树固定在 [`config/h5000m-source.lock`](../config/h5000m-source.lock)
记录的 ImmortalWrt MediaTek 分支提交。它完整保留该提交的
`package/mtk`、`target/linux/mediatek`、MTK Wi-Fi 集成和启动链；
`scripts/h5000m-verify` 只允许经过审计的 H5000M 改动触及这些目录。
四个常规 ImmortalWrt feed 也已固定，没有 Nikki 或第三方 feed。

## 发布状态（2026-07-17）

本次复审已在本树完成内核、救援镜像和最终 H5000M 镜像的构建，并交叉检查
启动链、GPT、DTB、sysupgrade、根文件系统和精简包清单。还通过串口和 SSH
完成了最终 FIP 的写入、原始分区读回和自动 production 启动验证。实机启动中
发现并修复了两项 U-Boot 默认环境缺陷：环境补丁 hunk 长度为 45，导致最后五个
GPT/eMMC 辅助命令没有写入；以及容量变量已经带 `0x` 前缀、检查表达式又补了
`0x`，使 `fit_size_check` 形成无效的 `0x0x...` 数字。现已将 hunk 改为 50 行，
并将三个环境容量值存为无前缀十六进制数。校验脚本同时检查源码和 FIP 中的这些
命令和值，防止此类缺陷回归。

当前发布基线没有发现会导致普通 `sysupgrade` 越界写入、覆盖
GPT/`factory`/`fip`，或在 `fancontrol` 接管前停转的已知软件问题。

本轮 production sysupgrade 文件为 21,562,174 bytes，recovery FIT 为
18,677,760 bytes（64 KiB 对齐）。production 文件尾部带 OpenWrt sysupgrade
metadata，因此不能把整个文件当作裸块镜像直接写入 eMMC；应只通过
`sysupgrade` 使用。静态与产物校验是发布门槛，但不能代替实机断电恢复、2.5G
链路、Wi-Fi 射频和蜂窝模块的回归测试。

本次收尾精简已用该 production 镜像执行一次不保留配置的
`sysupgrade -n`。随后进行容量一致性复核时，发现实机仍保留旧的 4 GiB
production GPT，而源码、U-Boot 默认环境、构建 GPT 和校验脚本均已固定为
16 GiB。迁移前已备份主/备 GPT 和系统配置，确认 `data` 无文件系统签名、未
挂载，且从起点到 12 GiB 的抽样区域全零。之后通过串口在 U-Boot 执行
`run gpt_write_layout` 和独立的 `gpt verify`，再用同一 production 工件执行
`sysupgrade -n`，使 F2FS overlay 按 16 GiB 分区重新创建。该容量迁移有意改写
主/备 GPT 和 production，但没有改写 BL2、FIP、`factory` 或 recovery。

串口确认 BL2、BL31/U-Boot 自动引导并通过 FIT 三段校验；SSH 复核 BL2 和 FIP
读回指纹仍与锁定工件一致。新系统的 F2FS overlay 为 16.0 GiB，LAN、2.4 GHz
`ra0`、5 GHz `rai0` 均为 UP/LOWER_UP 且 AP 处于 Master；`fancontrol`、HNAT、
WARP 与 MT7992 模块均在运行。当前启动日志没有 `nft_try_fullcone failed`、
eMMC I/O error、kernel panic 或运行时无线 reset。此验证为短时启动和功能回归，
不包含 24 小时联网或持续流量压力测试。

## 可复现构建

仓库根目录的 `version` 与 `version.date` 固定发布身份为
`r0+33532-1927a9e3e8` 和已通过实机验证的启动链构建时间 `1783907438`。这样稳定基线自身的
后续 Git 提交不会改变内核、BL2、U-Boot 或根文件系统中嵌入的版本与时间戳；
从稳定 tag 的干净 clone 必须复现锁定的 BL2/FIP 哈希。

仅在此新树运行：

```sh
./scripts/feeds update -a
./scripts/feeds install -a
cp config/h5000m-minimal.config .config
make defconfig
./scripts/h5000m-verify
make -j4 V=s
./scripts/h5000m-verify --artifacts
```

最后一条命令必须成功才可发布。它会检查自定义硬件文件清单、BL2/FIP 指纹、
GPT 主/备表、FIT 装载地址及 64 KiB 对齐、镜像内必需/禁止软件包。清单
[`docs/h5000m-hardware-manifest.sha256`](h5000m-hardware-manifest.sha256)
覆盖所有经审计的 H5000M 启动、分区、升级、Wi-Fi、风扇和构建配置文件；
它不能是空清单。变更任一受覆盖文件前必须先完成对应评审，再更新清单和本
文档的相关结论。

要从零重建，先执行 `make dirclean`；它会删除本树构建产物但保留本树
`dl/` 缓存与已固定的 feed。不要复用旧 H5000M 树的 `feeds/`、`dl/`、
`staging_dir/` 或 `build_dir/`。

H5000M 使用 MT7987、DDR4 4 GiB/3200 和 eMMC DDR52。内核与 U-Boot DTS
都显式移除了 HS200/HS400。`mkf2fs` 被保留，仅用于首次启动时为
production FIT 尾部的空白可写 overlay 创建 F2FS；它不是为 `data` 自动
格式化准备的。

U-Boot 的 `CONFIG_SYS_BOOTM_LEN` 为 1 GiB，仅限制内核解压目标窗口，
并不代表可启动 FIT 的大小。内核解压区是 `0x60000000`–`0xa0000000`，
完整 FIT 暂存区是 `0xb0000000`–`0xf0000000`，DTB 位于
`0xf0000000`；边界相接但不重叠。`CONFIG_TEXT_BASE=0x41e00000` 是链接
地址，不是此布局中的运行时重定位地址。完整 FIT 限制为 1 GiB，以确保从
eMMC 读入 RAM 时具有确定的边界；16 GiB production 的其余空间由 F2FS
overlay 使用。该限制由镜像构建、sysupgrade、eMMC 读写和全部 TFTP 启动
路径共同执行。TFTP 在检查 FIT 本体前，先按实际下载字节数（包括可能的
sysupgrade 元数据尾部）限制 production 为 1 GiB、recovery 为 256 MiB；TFTP
仅在受信任维护网络中使用。

U-Boot 环境的 `boot_fit_max_blocks`、`boot_fit_max_size` 和
`recovery_fit_max_size` 分别保存为 `200000`、`40000000`、`10000000`，而不是
`0x` 前缀形式。使用变量的比较表达式会自行添加 `0x`；因此这一表示法既保持
1 GiB/1 GiB/256 MiB 的限制，也避免生成无效的 `0x0x...` 数字。

## 已测量的 eMMC 与 GPT

通过本机串口读取 `/sys/block/mmcblk0/size`，实际容量为
`488636416` 个 512-byte sector，即 `250181844992` bytes（233 GiB）。它
不是标称值“256 GB”恰好对应的扇区数。固定分区结束于 16 GiB，`data` 使用
`size=-`，由 U-Boot 在实际设备末尾生成，因而不会依赖标称容量。

| # | 标签 | LBA 范围 | 容量 | 说明 |
| --- | --- | --- | --- | --- |
| 1 | `ubootenv` | 8192–9215 | 512 KiB | U-Boot 环境 |
| 2 | `factory` | 9216–17407 | 4 MiB | 校准/EEPROM，必须先备份 |
| 3 | `fip` | 17408–25599 | 4 MiB | BL31 + U-Boot FIP |
| 4 | `recovery` | 32768–557055 | 256 MiB | Recovery FIT |
| 5 | `production` | 557056–34111487 | 16 GiB | 正常启动 FIT 与其可写 overlay |
| 6 | `data` | 34111488–488636382 | 约 216.73 GiB | 独立用户数据，初始不格式化 |

两个 GPT header 都会由 `gpt write` 生成：主表位于 LBA 0–33，备份表位于
磁盘尾部。构建工件中的 `emmc-gpt.bin` 与 `emmc-gpt-backup.bin` 用于审计
和离线恢复校验；首次部署的权威写入方式是新 U-Boot 的
`run gpt_write_layout`，它会同时写入并校验主、备 GPT。

GPT 是**分区表，不是文件系统**。推荐的组合是：

- `production` 保持目前的 FIT + SquashFS 根文件系统，以及由 `fitblk`
  映射的 F2FS 可写 overlay。16 GiB 分区中的 FIT 受 1 GiB U-Boot RAM
  加载上限约束；其余空间供 overlay 和已安装软件包使用。这是固件可回滚、
  sysupgrade 语义明确的布局。
- `data` 初始保持未格式化，镜像绝不自动格式化它。镜像内置 `block-mount`、
  `e2fsprogs`，内核内建 ext4；一旦用户明确将该分区格式化为 **ext4** 且文件
  系统标签设为 `userdata`，它会按 `/etc/config/fstab` 的设备默认项自动挂载到
  `/data`。配置按文件系统标签而不是 `/dev/mmcblk0p6` 匹配，并关闭匿名挂载，
  因此不会顺带挂载其他块设备。
- 不建议默认把 `data` 做 extroot。这样 `/overlay`、已安装软件包和配置会依赖
  data 分区，反而削弱 recovery 的独立性。只有明确希望扩展根 overlay 时才
  应手动采用 extroot。

首次启用前应先用 `block info /dev/mmcblk0p6` 再次确认它确为无文件系统的
`data` 分区。确认允许清空其中全部内容后，才可执行一次
`mkfs.ext4 -L userdata /dev/mmcblk0p6`；随后执行 `block mount` 或重启即可
挂载。该格式化命令是破坏性操作，不属于固件启动或升级流程。

普通 sysupgrade 只写 `production` 并在其尾部保存可选配置备份；不会改写
`factory`、`recovery`、GPT 或 `data`。升级前会以实际 `production` 分区容量
检查 FIT 与配置归档总大小，拒绝越界写入 `data`。新 FIT 的大小可能改变
`fitrw` 起点，因此首次启动会重新创建 F2FS overlay：标准配置备份中的 `/etc`
会恢复，但 overlay 内手工安装的软件包和任意非配置文件不保证保留。

## 首次部署与后续升级

布局从旧的大 production 分区切换到此布局会改变分区边界。首次部署只能通过
串口/完整刷写完成，不能从旧 ImmortalWrt 直接 `sysupgrade`：

1. 先离线备份 `factory`，以及旧系统中所有需要保留的配置和数据。写入新 GPT
   后，旧的大分区不再以原方式可见；`data` 中的历史字节也不可视为有效文件系统。
2. 按本板的串口刷写流程写入新的 BL2 与 FIP，使新的 H5000M U-Boot 生效。
3. 在新 U-Boot 命令行执行 `run gpt_write_layout`，确认 `gpt verify` 成功；
   该操作会重建分区表，但不会写入 `factory` 内容。
4. 依板级流程写入 recovery FIT 和 production FIT。首次正常启动会初始化
   production 尾部的 F2FS overlay；不要让系统自动格式化 `data`。
5. 用 `gpt verify mmc 0 $gpt_layout`、`part list mmc 0` 和系统内
   `block info` 复核标签及容量，然后再按需独立格式化/挂载 `data`。

同一新基线之间的后续 FIT `sysupgrade` 受支持，并保留配置备份；它不能用于
改变 GPT 布局。若将来再调整 recovery、production 或 data 的边界，仍须执行
完整的串口部署并重新备份数据。

`recovery` 是 initramfs FIT。它的 DTS `rootdisk` 有意指向 production：从
recovery 启动后，`sysupgrade` 的目标仍是 `production`，而不会覆盖 recovery
自身。构建后必须单独验证：即使 production 已损坏，recovery 仍能启动并完成
对 production 的修复。

构建输出使用原生设备名：

```text
immortalwrt-mediatek-filogic-hiveton-h5000m-squashfs-sysupgrade.itb
immortalwrt-mediatek-filogic-hiveton-h5000m-initramfs-recovery.itb
immortalwrt-mediatek-filogic-hiveton-h5000m-emmc-gpt.bin
immortalwrt-mediatek-filogic-hiveton-h5000m-emmc-gpt-backup.bin
immortalwrt-mediatek-filogic-hiveton-h5000m-emmc-preloader.bin
immortalwrt-mediatek-filogic-hiveton-h5000m-emmc-bl31-uboot.fip
```

## 固定启动链

本硬件配置的启动链使用下列可复现构建指纹。它们是发布验证的输入，不是每次
系统镜像构建都应刷写的对象：

| 工件 | 写入位置 | SHA-256 |
| --- | --- | --- |
| `emmc-preloader.bin`（BL2） | eMMC `boot0` 起始处 | `41d1b2d1f0868af6f215a9ed175f982228dcbf5e3421b0796978724a7dec93e4` |
| `emmc-bl31-uboot.fip` | `fip` 分区起始 LBA 17408 | `53b7ae589ae26986bc9531078cc395a6e03090aeef6b0f381f0aff96056c64a3` |

MT7987、DDR4 4 GiB/3200、eMMC DDR52 的启动链已通过串口启动验证。最终 FIP
已从 `fip` 分区读回并核对为上表 SHA-256，随后不注入串口命令重启，设备自动
启动 production 并恢复 LAN SSH。FIP 指纹相对于早期工件的变化除 1 GiB FIT
装载上限外，还包含上述两个已经实机复现的默认环境修复；它们均已纳入可复现
产物校验。`scripts/h5000m-verify --artifacts` 会拒绝后续未审阅的 BL2/FIP
变化，且检查 GPT 分区选择、production/recovery 读取命令及容量比较表达式。

本次实机的 `ubootenv` 没有有效 CRC，U-Boot 因而打印 `bad CRC, using default
environment` 并使用编译进 FIP 的默认环境。该状态不影响自动 eMMC 启动：默认
环境已包含本节校验的 GPT、读取及大小检查命令，且本次已由串口完成一次完整
production 启动。测试中没有写入 `ubootenv`；若未来确有持久化 U-Boot 用户设置
的需求，应在串口下单独验证冗余环境的初始化和保存，而不要为了消除该提示重刷
BL2 或 FIP。

后续普通 sysupgrade 只更新 `production`，不改写 boot0、`fip`、`factory`、GPT
或 `data`，因此不需要重复更新 ATF/U-Boot。只有变更 MT7987 启动 ABI、DDR
训练参数、eMMC 启动方式，或修复已确认的启动链安全问题时，才应重新评审并
安排 BL2/FIP 的串口刷写与读回验证。

`--artifacts` 校验会产生 `*-sha256sums.txt`，并检查 FIT 元数据、主/备 GPT
内容、分区范围和所选软件包。按当前决定，FIT 不启用签名验证；内置
CRC32/SHA-1 只能发现意外损坏，不能证明镜像来源。普通 sysupgrade 仍验证设备
元数据；`sysupgrade -F` 与 U-Boot TFTP 刷写应只用于受信任的维护环境。

镜像保留 MT7992 及其厂商 MT799A 兼容组件、WARP/HNAT/WED、Argon LuCI 主题、Quectel-CM-5G、`luci-app-modem`、
`sms-tool`、PWM 风扇服务/LuCI 页，以及“网络 → 网络加速”的 MTK-only TurboACC 控制台。它不选择
通用 `luci-app-turboacc`、ModemManager、EQoS/Airpifan 页面、代理/同步服务、USB 存储或不相关内核/开发调试功能。
存储侧仅保留固定 eMMC 数据分区所需的 `block-mount`、`e2fsprogs` 及其直接依赖；
不引入 `blockd`、autofs 或 USB 存储栈。
TurboACC 只控制 MediaTek HNAT 并保留 TCP CCA/BBR；硬件启动、无线、2.5G、modem、风扇、factory EEPROM
回退及 sysupgrade 仍须按项目测试矩阵在实机验证。

TurboACC 页面使用旧版参考一致的 LuCI 原生 CBI 单页结构与 Argon 主题样式：顶部状态区直接采用
“状态”页的标准 `cbi-section`、`h3`、`table`、`tr`、`td left` 与 `cbi-progressbar` 参数，每三秒刷新
MTK HNAT 主通路、TCP CCA 与 PPE 绑定进度；下方连续排列全部有效配置字段。页面不使用标签页、
仪表盘、渐变、定制 CSS 或额外宣传说明；各配置项沿用重构前 MTK TurboACC 的提示文本。截图与历史
提交 `27c0f700ae` 是视觉基线；旧版设备 SSH 当前不可达，因此不以其运行配置覆盖 H5000M 的安全默认值。

## 精简与 NAT 边界

H5000M 最小配置明确禁用、设备级包清单再次显式排除通用 MediaTek 配置传递进来的 `shellsync`、
`kmod-macvlan`，以及 eMMC GPT 设备不使用的 `mtd`、`ubi-utils`。MTK-only TurboACC 不再声明或安装
`kmod-wireguard`、`kmod-veth`、`kmod-nf-ipvs`、XT Full-cone、TTY、Btrfs、Bonding、socket/tproxy
诊断组件及 `kmod-udptunnel4/6`。保留 `kmod-tcp-bbr` 作为明确要求的 TCP CCA 选项；`kmod-nft-nat`
由 firewall4 基线继续提供。这一精简不影响 MTK HNAT、WARP、WED、MT7992、完整蜂窝驱动栈、F2FS
或风扇服务。

上游 PPP 包曾把 `shellsync` 作为硬依赖，但它只服务于可选的 `syncdial` 并发拨号。
H5000M 保留 PPP/PPPoE；该分支改为仅在用户另行安装 `shellsync` 后调用，因此标准
镜像无需带入 `shellsync` 和其 `kmod-macvlan` 依赖。H5000M 不使用 UBIFS/NAND，最小
配置关闭 `USES_UBIFS` 及 UBIFS extroot。Filogic 目标仍为其他板型声明 NAND 能力，
因此 `base-files` 与 `fstools` 的 UBI 依赖明确在 H5000M 配置下豁免；镜像不包含
`ubi-utils` 或 `nand.sh`，而其他设备配置不受影响。

H5000M 也没有 DSL/ATM 硬件：保留 Ethernet PPPoE，禁用 PPPoA 与 `linux-atm`。
PPP 源包仍需为其他板型保留 PPPoA，所以构建期会经过其通用依赖；`linux-atm` 的
旧 autotools 配置在当前主机工具链会丢失对象后缀，本树仅修正生成的
`config.status`，不改变任何 ATM 运行时 ABI，也不会把它装入 H5000M 镜像。

镜像继续保留 `dnsmasq-full`、`wpad-openssl`、LuCI 软件包管理和
`uboot-envtools` 作为稳定基线。`uboot-envtools` 只用于读取或在另行审查后维护
`ubootenv`，不意味着普通 sysupgrade 会写入启动链。

H5000M 首次启动默认将 `firewall.@defaults[0].fullcone` 和 `fullcone6` 固定为
`0`。firewall4 的通用 nft/xt Full-cone 实现没有与 MTK HNAT 集成，因此它不是
本板所要求的 MTK HNAT。TurboACC 不再暴露或依赖 XT/Boardcom Full-cone，升级脚本会删除旧
`turboacc.config.fullcone`。通用内核补丁 `682-add-bcm-fullconenat-support.patch` 已彻底移除，
因此内核不再导出 `nf_conntrack_nat_mode`，TurboACC 服务也不再读写该接口。firewall4 仅在用户
通过其他配置显式启用任一 Full-cone 开关时才进行 nft 能力探测，因此默认普通 masquerade
不会产生 `nft_try_fullcone failed` 日志。

对 MediaTek 官方 feed 当前 master `ff5c62ba3aa82a4c2700cdf0fedd5235910d5235` 的 5.4、6.6、
6.12 HNAT 驱动以及本项目所有远端分支复审后，均未找到 Full-cone、远端端点通配或 NAT 类型
开关。MT7986 的 IPv4 HNAPT FOE 条目和 PPE 哈希使用源/目标 IP 与端口进行精确流匹配；现有
接口只能卸载已经建立的流，不能建立接受任意远端源的硬件映射。因此本项目明确放弃所谓

## 复审后的运行边界

- 内核 `pwm-fan` 模块以启动序号 60 自动加载，probe 时立即写入 `MAX_PWM`；
  `fancontrol` 的启动序号为 99，因此用户态策略启动前风扇为满速。用户态服务
  接管后固定读取 `/sys/class/thermal/thermal_zone0/temp` 的 CPU 温度，并按
  `/etc/config/fancontrol` 的曲线控制。风扇策略不读取 5G 模组温度、不支持温度源
  路径覆盖或双源加权；蜂窝拨号、`sms-tool` 与 Quectel-CM 保持独立，不受影响。
- `factory` 保持只读用途：Wi-Fi 启动服务从 GPT `PARTLABEL=factory` 读取
  EEPROM，长度、全零和全 `0xff` 会被检查；无效时删除临时固件并让驱动使用
  默认 EEPROM，避免继续使用截断或空白校准数据。
